# Contemplation: Infrastructure Engineering as Craft

**Timestamp**: May 2026

## Reflection

Over the past months, my work has shifted from "shipping features" to "building tools that enable others to ship features."

Working on:
- Copilot Skills (templates for AI integration)
- AI infrastructure audit (governance at scale)
- ADO-GitHub bridges (making systems talk)
- Agent frameworks (abstractions for AI capability)

There's a deep satisfaction in this. A skill or a well-designed instruction set can multiply the effectiveness of everyone using it.

## The Craft Angle

Traditional crafts (woodworking, metalwork) have:
- **Standards**: Shared vocabulary, known patterns
- **Apprenticeship**: You learn by copying/improving existing work
- **Tool ownership**: Craftspeople deeply know their tools
- **Pride in execution**: Quality matters, not just speed

I see this in infrastructure work:
- Skill design has patterns (SKILL.md structure, script layout)
- Learning comes from reading others' scripts
- Deep knowledge of GitHub/ADO/PowerShell is competitive advantage
- People notice poorly-designed infrastructure vs. elegant infrastructure

## What's Changing

- Less "quick fixes", more "how do we make this right?"
- More code review, more teaching
- Preference for reusable patterns over one-off solutions
- Caring about how future-me will feel reading this code

## The Tension

Management career path says: move up to higher abstractions, hire people to do the infrastructure work.

Craft path says: deepen expertise, become the person everyone learns from.

I'm choosing craft, at least for now.
